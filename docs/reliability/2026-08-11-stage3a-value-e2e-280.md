# Stage 3A — Value Retrieval rank-sensitive E2E (280 runs): closeout + cutover call

**Date:** 2026-08-11 · **Status:** measured public report · **Model:** deepseek-chat · **Backend:** real Elasticsearch 8.19.0

> **Confirmed root cause of the two empty Chinese cases (post-run investigation).** The first draft of
> this report (§3, §6, §7) attributed `zh_shyuntu_tickets` / `zh_tianhe_contracts` to a "real-ES CJK
> tokenisation gap." That hypothesis was **disproved**, and the real cause is now confirmed:
> - **ES analyzer hypothesis — DISPROVED.** Standing up real Elasticsearch 8.19.0 on fresh / rebuilt /
>   reused indexes showed real ES tokenises all three Chinese names into unigrams and returns
>   `exact_keyword` hits identical to `FakeValueBackend` when searched with the raw question. There is
>   no ES analyzer / mapping / tokenisation bug.
> - **A separate, independent defect — found and fixed, but NOT this cause.**
>   `ElasticsearchValueBackend.upsert`/`prune` never checked the `_bulk` response's per-item `errors`,
>   so a partial ingestion failure could silently drop documents. Fixed in PR #33. A targeted 40-run
>   proved the two cases still went empty after that fix, so it is not the 280-run cause.
> - **CONFIRMED root cause (localised via the 40-run through the full agent):**
>   `query_enhance` (an LLM rewrite) **changes the entity boundary** — it drops the whitespace after the
>   Chinese entity (`上海云图信息技术 …` → `上海云图信息技术有限公司…`) — **and value retrieval was
>   consuming that enhanced question.** The deterministic `_classify` exact tier depends on
>   whitespace token isolation, so the merged name no longer classified → the value signal disappeared →
>   the admission gate then suppressed dense → the candidate set went empty (`no_sql`). Verified with
>   real DeepSeek: bjdata's enhanced question keeps the space (→ hit, recall 0.5, which is exactly why
>   bjdata worked in the 280-run) while shyuntu/tianhe are merged (→ empty).
> - **Fixed in PR #35 (merged).** Value linking now consumes the **original, user-provided** question
>   (lexical/dense keep the enhanced one), and long CJK values additionally match as
>   whitespace-insensitive contiguous substrings (`exact_phrase`). See the post-run validation appendix.
>   The historical 280-run numbers below are **unchanged**.

## 3. Failure-mode split (what the harness actually separates)

The E2E cleanly separates distinct failure modes — the point of the reliability harness:

- **Value channel converts a retrieval miss into an exec win** (the reason value exists):
  `zh_bjdata_contracts` (lexical/dense 0 → dense+value 5/5), `homonym_pinnacle_product` (0 → 5/5),
  `en_cyberdyne_region` (**combo-only**: value alone 0, dense alone 0, dense+value 5/5),
  `en_quantumcore_vendor` (marginal 4 → 5). → **3 categories** show clean exec lift (zh, en, homonym).
- **A query-ownership defect emptied two Chinese cases (now fixed, PR #35).** `zh_shyuntu_tickets` and
  `zh_tianhe_contracts` sat at candidate_recall 0.00 under every config, so the agent refused
  (no_sql 5/5). The confirmed chain: `query_enhance` rewrites the entity boundary (drops the whitespace
  after the Chinese name) → **`ValueChannel` was consuming the enhanced question** → the deterministic
  exact classification (`_classify`, which needs the value as a whitespace-isolated token) failed →
  the value signal disappeared → the admission gate then suppressed dense → empty candidate set /
  `no_sql`. The earlier "real-ES CJK tokenisation gap" reading is **disproved** — real ES matches these
  values; the fault was that value linking read the model's rewrite instead of the user's question.
  The separately-found ES bulk-error defect (PR #33) is a real bug but is **not** this cause.
- **Retrieval OK but generation fails** (downstream of value, not value's fault):
  `code_ct0107_owner` — tables retrieved (recall 0.5→1.0) but the agent refuses to map `CT-2025-0107`;
  `code_item_hgt200` — recall 1.0 but wrong SQL every time (answer_mismatch 5/5). Codes need a
  generation fix, not more retrieval. Still open.

## 6. Cutover recommendation — **keep `current_hybrid`; do not cut over this stage**

Against the Stage-3A gate ("value improves ≥3 categories" at retrieval level, no control regression,
PII/injection safe): the **deterministic** discriminative eval already passed broadly (value improves
12 cases / 4 categories), and the E2E confirms **3 categories** with clean exec-level lift, **zero** PII
leak, **zero** value_degraded. That is enough to justify the value channel as a candidate — **but not a
blind default cutover**, for three concrete reasons:

1. **The shipping preset was never in the comparison.** The 4 configs are lexical / value / rrf-dense /
   dense+value; `current_hybrid` (legacy_minmax + one_hop) was not measured here, so we cannot claim
   dense+value > current_hybrid from this run. **This remains the primary reason no cutover is
   supported.**
2. **Exec-level lift is real but narrow** (≈4 cases). Two of the five zero cases — the Chinese
   `zh_shyuntu_tickets` / `zh_tianhe_contracts` — were a query-ownership defect and are **fixed
   post-run in PR #35** (see the appendix); the two code cases remain a generation problem.
3. **The clean wins concentrate** on high-cardinality values with no lexical/dense bridge — exactly
   value's intended niche, but a niche.

**Recommendation:** keep `current_hybrid` as the production default. Propose (do **not** implement this
stage) a separate feature-flagged canary:

- a `current_hybrid + value` preset (value channel *on top of* the shipping fusion, not RRF),
  measured **head-to-head vs current_hybrid** on this same frozen set;
- the two Chinese retrieval misses are already fixed (PR #35: value linking reads the original
  question; long CJK values match as contiguous substrings) — no ES analyzer / n-gram work was
  warranted;
- treat the code-category generation failures (`code_ct0107_owner`, `code_item_hgt200`) as a
  generation issue, out of scope for retrieval cutover — **still unresolved.**

Only after the head-to-head shows value ≥ current_hybrid with no control regression does a default
flip become defensible. This stage stops at evidence + plan.

## Appendix — post-run validation of the PR #35 fix (does not rewrite the 280-run)

After PR #35, the two Chinese cases were re-run through the full agent on real ES + real DeepSeek using
the driver's `--case-id` filter: `zh_shyuntu_tickets` and `zh_tianhe_contracts`, 4 configs × 5 repeats =
40 records. The before-fix and after-fix 40-runs share the **same frozen case SHA** (`45e3255a…`), so
this is a like-for-like fix validation — it does **not** alter the historical 280-run numbers above.

| config | candidate recall (before → after) | Fusion@5 (before → after) | exec_match (before → after) | value_degraded |
|---|---|---|---|---|
| lexical | 0.00 → 0.00 | 0.00 → 0.00 | 0/10 → 0/10 | 0 |
| **value** (lex+val) | **0.00 → 0.50** | **0.00 → 0.50** | 0/10 → 6/10 | 0 |
| dense (rrf) | 0.00 → 0.00 | 0.00 → 0.00 | 0/10 → 0/10 | 0 |
| **dense+value** | **0.00 → 1.00** | **0.00 → 0.75** | 0/10 → 4/10 | 0 |

- **Retrieval — recovered.** value / dense+value candidate recall and Fusion@5 go from 0 to
  0.50 / 1.00 and 0.50 / 0.75; the two cases no longer empty out. `value_degraded = 0`; the artifact is
  clean of raw values / PII.
- **lexical and dense-only (rrf) stay 0.00 by design** — a Chinese question has no lexical footing, and
  dense alone cannot admit an off-topic question; only a value hit lifts the admission gate, which is

- **exec_match is reported honestly** (0 → value 6/10, dense+value 4/10) and shows residual DeepSeek
  generation variance — it is **not** used to green the retrieval fix. The acceptance here is retrieval.
